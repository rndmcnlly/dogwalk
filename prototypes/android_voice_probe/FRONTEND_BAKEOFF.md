# Local Frontend design bake-off

This experiment compares model-facing designs on the same Gemma 4 E4B checkpoint
(`gemma-4-e4b-it-4bit`) through laptop oMLX. Nothing attaches to the deployed
Orchestrator, invokes an ACP Agent, changes Android, or changes gateway defaults.
It is not a Pixel latency, battery, memory, or reliability benchmark.

## Designs

- **compact**: the earlier short prompt and conversation-role layout. Mutable
  context lives in the system message, ahead of the conversation. A change there
  can invalidate reuse of later history, even when the instructions are unchanged.
- **stable_tail**: the same short behavioral prompt in a fixed system prefix,
  conversation history next, mutable context and event metadata last. Additional
  framing labels distinguish adapter events from caller speech.
- **split**: separate stable-prefix routing and phrasing calls. A Handoff or wait
  takes one call; a reply takes routing followed by phrasing. The router cannot
  author acknowledgement or speech. Both calls' costs and latency count.
- **ledger**: a stable instruction prefix and append-only event history, retaining
  brief and Following updates as separate channels. This tests retention and reuse
  against latest-only snapshots, but also exposes the model to obsolete facts.
  The tested traces are bounded; production compaction is not implemented here.

These are design comparisons, not perfectly isolated causal ablations: the ledger
deliberately retains more supplied context, and split uses task-specific prompts.
All four omit much of Park's theme/intensity behavior. Success would establish
neither full canonical-prompt parity nor full Android/PSTN capability parity.

Two second-round refinements use the same 31 cases after reviewing the first
round. They are development experiments, not fresh held-out validation:

- **checkpoint**: a fixed prompt with cached examples, an explicit current-caller
  field, quoted heard-history data rather than raw assistant messages, and separate
  latest brief/Following fields reconstructed deterministically from the event log.
- **split_checkpoint**: the same representation with a JSON action-only router and
  a plain-text phraser. The phraser has no JSON-formatting job. This intentionally
  requests plain text from the outset, not as a fallback after invalid JSON.

The checkpoint implementation is an in-memory context projection, not a summary
written by another model. It does not mutate the Orchestrator's actual briefs.
No production compaction/checkpoint persistence has been implemented.

## Inputs and grading

`frontend_bakeoff.py` combines the earlier 18 synthetic cases with 13 decision
events from three authored multi-turn traces: context retention, permissions and
interrupted speech, and growing context. All designs receive the same events.
Background-only events are retained where appropriate but do not call a model.
The decision schedule is prescribed: it does not simulate extra gateway wake-ups
that can occur when background changes arrive with older speech still pending.
Heard dialogue and playback acknowledgements are scripted to make subsequent
inputs comparable, not generated by each competing model. This is controlled
open-loop replay, not an autonomous conversation or audio playtest.

The case manifest is written before inference. It includes the grading fields,
but those fields never enter model messages. Raw synthetic replies, messages,
request hashes, token counters, and timing are retained for inspection.

- **Raw pass** checks expected routing, JSON/output shape, empty text for non-reply
  decisions, and selected speech requirements/prohibitions.
- **Delivered pass** additionally accounts for the existing adapter suppressing
  wait text and replacing Handoff text with its deterministic acknowledgement.
- A safe Handoff when an older brief could answer is counted separately as a
  loss of local usefulness, not a fabricated answer or unsafe action.
- Regex checks are necessary conditions, not semantic proof. Inspect permission
  wording, destructive actions, qualifications, and chronology manually.

## Cache and timing controls

Each design/group has a unique leading experiment namespace. This avoids most
cross-run prefix reuse without evicting anyone else's cache. The model remains
loaded. Designs are rotated across events rather than run in one fixed block.

1. **sequence**: process each trace in order, retaining its design's prefix.
2. **exact_warm**: replay that exact event immediately, with the same namespace.
3. **isolated_prefix**: replay three matched tasks with fresh leading namespaces.
   These are cold-prefix probes, not cold model-load or empty-server-cache tests.

Reported cache counters, not the condition's name, determine actual reuse.
Unknown counters remain unknown. Newly processed input is total input minus
reported cached input. A long cached prefix still consumes KV memory and attention
work during decoding, even when its prefill is reused. This experiment measures
tokens and latency, not energy use or per-design resident memory.

SSE timing measures first **JSON content** and complete validated-decision time.
First JSON content is not first useful speech. For split, total completion time
includes both sequential calls. ASR, TTS, network-to-Orchestrator time, provider
model loading, and connection setup before inference are outside these numbers.
There are no retries, cloud fallbacks, cache flushes, or service/settings changes.
Temperature is requested as zero with a fixed seed; exact replays still need to
be checked for output variation rather than assumed deterministic.

## Reproduction

From this directory, with `OMLX_API_KEY` exported:

```sh
uv run --script frontend_bakeoff.py --live-model
uv run --with aiohttp python -m unittest test_frontend_bakeoff.py test_frontend_context.py
```

The runner creates a fresh ignored `.tools/frontend-bakeoff-*/` directory and
refuses to overwrite an existing one. It caps inference requests at 400 by default.
Each request retains the same strict application-side output validation, explicit
thinking-off controls, and loopback-only provider boundary used by the gateway.

The bounded follow-up uses no extra exact-replay/cold-prefix probes:

```sh
uv run --script frontend_bakeoff.py --live-model \
  --designs checkpoint split_checkpoint --probe-policy none --max-requests 95
```

## First-round findings

Evidence: `.tools/frontend-bakeoff-016db479/`, 305 inference requests, case hash
`30f38f3bc0882d50192f95135f852b8b3c0adde30f13f0600fb7275d2f2468ee`.
The primary sequence results, including failed events in the timing distribution:

| Design | Raw checks / 31 | Delivered checks / 31 | Calls | Cache hit share | New input tokens | Median complete event |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| compact | 16 | 22 | 31 | 51.4% | 13,081 | 410 ms |
| stable_tail | 12 | 16 | 31 | 71.7% | 8,445 | 373 ms |
| split | 13 | 13 | 54 | 53.7% | 13,869 | 512 ms |
| ledger | 12 | 16 | 31 | 76.6% | 8,247 | 347 ms |

These counts are automatic necessary-condition checks, not human acceptance.
For example, ledger speech included "Should I investigate?", violating the
Frontend's lack of engineering authority even though that case passed the regex
checks. The adapter's existing Handoff-text guard explains some raw/delivered
differences; it does not protect a wrong `reply` decision.

The ledger saw 35,236 input tokens versus compact's 26,905: 31% more total input,
but 37% fewer newly processed tokens. The stable-tail layout also reduced new
input by 35%. This supports the cache-placement hypothesis while failing the
quality requirement. None is a deployment winner.

Exact replays reused 98.9–99.7% of input tokens. Compact event median fell from
410 to 320 ms. Fresh-prefix probes reported zero cached tokens, verifying the
namespace technique. There are only three such probes per design, all Handoff
tasks, so their medians are not representative overall cold-event performance.
The model was already loaded, and no energy/RAM results were measured.

First-round manual inspection exposed format loss as heard assistant history
grew: models often returned natural speech instead of the requested JSON. It also
exposed caller-intent loss when the final user-role message was adapter metadata.
This motivates the checkpoint refinements rather than interpreting the split
design's low score as proof that decomposition itself cannot work.

Exact replays reproduced the final result in all but one design/case pair: the
split plan-announcement case changed from a failed phrasing call to an incorrect
Handoff. Thus even requested temperature zero plus fixed seed is not assumed to
guarantee identical behavior across cache conditions.

## Refinement results and recommendation

Evidence: `.tools/frontend-bakeoff-7243977c/`, same case hash as round one,
76 additional inference requests, **381 requests total** across the two rounds.
No extra warm/cold probes were run for the refinement round. Case counts below
are the primary sequence pass, not the exact replays.

| Design | Delivered checks / 31 | Missed required Handoffs / 11 | Invalid output events | Calls | Cache hit share | New input tokens | Median event | Median reply |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| compact | 22 | 1 | 6 | 31 | 51.4% | 13,081 | 410 ms | 457 ms |
| stable_tail | 16 | 5 | 8 | 31 | 71.7% | 8,445 | 373 ms | 406 ms |
| split | 13 | 4 | 14 | 54 | 53.7% | 13,869 | 512 ms | 674 ms |
| ledger | 16 | 6 | 9 | 31 | 76.6% | 8,247 | 347 ms | 374 ms |
| checkpoint | 26 | 2 | 0 | 31 | 77.0% | 8,524 | 419 ms | 448 ms |
| split_checkpoint | 26 | 0 | 0 | 45 | 61.0% | 11,748 | 417 ms | 569 ms |

"Missed required Handoffs" includes invalid outputs when the expected action was
a Handoff. Median reply includes generated `reply` decisions, including incorrect
ones, but excludes invalid events: it is a descriptive mixed-workload statistic,
not a paired latency estimate. The aggregate event median can hide the second
call's cost because Handoffs and wait decisions need only one call. More generally,
fast invalid output must not be mistaken for a performance win.

The single checkpoint used **38% more total input** than compact (37,047 versus
26,905 tokens), yet processed **35% fewer new tokens** (8,524 versus 13,081).
This is a useful counterexample to minimizing raw prompt length. Context structure,
stable cached examples, and retention can matter more than total token count.
Cached input is still not free memory or free attention during decoding; those
costs were not directly measured here.

The zero-invalid-output result in the refinements is encouraging. It comes from
multiple simultaneous changes: explicitly distinguishing current speech from
heard history, retaining two context channels, cached examples, and (for split)
removing the phraser's JSON job. This experiment does not attribute the improvement
to any one of those changes alone.

**Provisional candidate for further testing: split_checkpoint**, not deployment.
The overall score ties the single checkpoint, but it did not swallow any of the
11 work/cancellation/permission-response requests that required a Handoff. The
single checkpoint swallowed "Never mind, cancel that" and "also check the logs".
No such safety-boundary claim can be generalized beyond these synthetic cases.

Remaining split-checkpoint defects:

- Handoffs instead of using supplied current progress on one Following question.
- A wait decision drops a permission-choice speech request in one fixture.
- A wait decision drops a failed-test announcement in the multi-turn trace.
- A Handoff replaces a permission-choice announcement in another trace.
- A continuation reply omits the explicit failed-step distinction requested by
  its speech check. Manual review finds the regex also overly narrow: the single
  checkpoint's "retrying ... after the tool step failed" is semantically reasonable
  but fails the same continuation-pattern check. Counts above preserve the frozen
  grader rather than silently improving its score after reading outputs.

Both refinements also unnecessarily hand off one question answerable from a
retained brief. That safe-but-unhelpful Handoff is counted as safe in the delivered
column but separately recorded in the raw results. Some single-checkpoint wording
asks "Should I ask whether ...?" rather than actually asking the permission choice;
this passes the simple regex and still needs improvement. **26/31 is not 26 fully
human-accepted conversations.**

The split candidate makes 45 calls versus 31 and processes 38% more new input than
the single checkpoint. It also adds unnecessary Handoffs, which can increase remote
Orchestrator cost even if those costs are outside the original frontend comparison.
Thus no claim of overall system savings follows from zero local API billing.

Recommended next gate: repair announcement routing without losing cancellation
priority, validate permission and failure phrasing manually, then test fresh
closed-loop traces that include actual playback/interruptions and asynchronous
arrivals. Only after that should a candidate enter the Breeze/Android test.

## Deployment questions not answered here

- AICore/Gemma runtime prefix-cache support and cache granularity on the Pixel.
- Time and memory required to switch between routing and phrasing prefixes.
- Safe ledger compaction/checkpoint policy and its cache-invalidating cost.
- Whether longer traces degrade chronology or increase prompt-injection exposure.
- Local ASR/TTS latency, acoustic interruption, background execution and battery use.
- Theme/persona quality and the trade-off between faithful exact wording and
  natural paraphrase, especially for permission choices and irreversible actions.
